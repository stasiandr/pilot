# Pilot

Мгновенный редактор кода для macOS. Нативный SwiftUI + AppKit, Liquid Glass.

Это не IDE. Задача — открыться быстрее, чем успеешь моргнуть, и дать
то, ради чего обычно ждёшь загрузки тяжёлой среды: найти файл, прочитать
его и поправить.

## Сборка

Нужны только Command Line Tools, Xcode-проект не требуется.

```
./run.sh                    # собрать и запустить с последним проектом
./run.sh ~/code/project     # открыть папку
./run.sh src/Program.cs     # открыть файл; корень — ближайший git-репозиторий
```

`run.sh` собирает debug-версию и перезапускает уже открытый Pilot. Лог
приложения пишется в `.build/pilot.log`. Release-сборка для замеров —
`CONFIG=release ./run.sh`, просто собрать бандл — `./build.sh`.

Для Liquid Glass нужен SDK macOS 26 (Xcode 26). На более старом Xcode
проект тоже соберётся — стекло заменится штатным `NSVisualEffectView`.
Само приложение работает начиная с macOS 14.

Иконка — документ Icon Composer `Resources/Pilot.icon`: открывается и
правится в Icon Composer из Xcode 26. `build.sh` собирает её через `actool`.
Без Xcode 26 бандл соберётся без иконки.

```
./run-tests.sh      # тесты ядра: индекс, поиск, .gitignore, лексер
```

**Rustlyn.** C# Pilot разбирает не сам, а компилятором
[Rustlyn](https://github.com/stasiandr/rustlyn) — он лежит отдельным
репозиторием и подключается статической библиотекой. `build.sh` собирает его
сам, если найдёт рядом:

```
git clone https://github.com/stasiandr/rustlyn ../rustlyn
./build.sh                          # соберёт и его, и Pilot
RUSTLYN_PATH=~/code/rustlyn ./build.sh   # если лежит не рядом
```

Нужен Rust ([rustup.rs](https://rustup.rs)) — без него сборка остановится
и скажет, чего не хватает. Тесты ядра (`./run-tests.sh`) собираются
отдельным пакетом и без библиотеки обходятся: в них подставляется заглушка,
и проверяется как раз то, что Pilot умеет сам.

## Интерфейс

Окно устроено по мотивам Xcode 26.

* **Навигатор** слева — плавающая стеклянная панель с тремя вкладками:
  дерево проекта, структура текущего файла и недавние проекты. Внизу —
  фильтр: в дереве ищет по имени файла без учёта регистра и показывает
  найденное раскрытым, в структуре — по имени объявления. `⌃⌘S` прячет
  панель; на стартовом экране её нет.
* **Вкладки** над редактором — открытые файлы. Каждый открытый файл встаёт
  во вкладку сразу за текущей, уже открытый — просто становится активным.
  `⌃Tab` возвращает на вкладку, где был перед этой: так прыгают между двумя
  файлами; с зажатым `⌃` каждый следующий `Tab` уходит дальше по недавним.
  Порядок меняется перетаскиванием, закрытая активная вкладка уступает место
  той, где был до неё: `⌘B`, прочитал, `⌘W` — и ты там, откуда пришёл.
  Больше 12 вкладок не держится: сверх этого закрывается та, где дольше
  всех не был, — кроме несохранённых. Вкладки помнятся для каждого проекта
  и возвращаются, когда его снова открываешь.
* **Jump bar** над редактором — путь до объявления под курсором. Каждый
  сегмент — меню соседей: файлы и папки рядом, объявления файла.
* **Тулбар**: имя проекта с веткой git, в центре — капсула активности:
  что открыто, идёт ли индексация, в каком состоянии языковой сервер.
  Клик по ней — то же, что `⌘P`.
* Строка с курсором подсвечена, внизу — строка и столбец.

На macOS 26 панели и кнопки — Liquid Glass, на 14–15 — штатные материалы.

## Редактирование

Курсор, набор, выделение, вставка, `⌘Z` без ограничения глубины — штатный
`NSTextView`, поверх которого правила для кода:

* **Return** держит отступ строки, после `{` уходит на уровень глубже,
  `{|}` раскрывается в три строки. В Python глубже — после `:`.
* **`}`** в пустой строке встаёт под парную `{`.
* **Backspace** в отступе стирает до предыдущей позиции табуляции.
* **Tab / ⇧Tab** на нескольких строках сдвигают их, `⌘/` комментирует.
* Отступ (пробелы или табы, их число) и перевод строки (LF или CRLF)
  берутся из самого файла, а не из настроек.

**Файлы и история правок.** У каждой вкладки свой буфер: свой текст,
своя история отмены, выделение и прокрутка. Ушёл на другую вкладку —
вернулся ровно туда же, с правками и `⌘Z`. Прокрутка запоминается первой
видимой строкой, а не координатой: раскладка текста ленивая, и координата
далёкой строки до раскладки — лишь оценка. Несохранённое видно по точке
на вкладке, после имени в jump bar, в капсуле тулбара и в красной кнопке
окна. Отменил всё до сохранённого состояния — файл снова чистый. Перед
закрытием вкладки с правками, сменой проекта и выходом Pilot спросит, что
с ними делать.
Сохранение атомарное, в исходной кодировке, права файла (бит
исполнения у скриптов) не теряются.

**Подсветка при наборе.** Синтаксическая модель правится инкрементально,
в том же вызове, что и текст: сдвигаются начала строк, а лексер
перезапускается с первой затронутой строки и останавливается, как только
состояние на входе в строку совпало с прежним. Обычный набор переразбирает
одну строку, независимо от размера файла; открытый `/*` честно
переразберёт хвост. Тесты гоняют сотни случайных правок и сверяют модель
с построенной заново.

**Автодополнение.** Список открывается сам — после первой буквы слова и
после символов, которые назвал сервер (`.`, `::`, `->`), — или по `Esc`.
Варианты — от языкового сервера (`textDocument/completion`): сигнатура
справа, бейдж вида, как у структуры файла. Сниппеты раскрываются, первая
заглушка параметра выделяется — начал печатать, и она заменилась.
Сопутствующие правки сервера (например, `using`) применяются вместе с
вариантом. Пока сервера нет или он не ответил — дополняются слова этого
файла и ключевые слова языка.

Правки уходят серверу сразу и только изменёнными кусками
(`textDocument/didChange`); серверу без инкрементальной синхронизации —
полным текстом, с задержкой и обязательно перед любым запросом.

## Что внутри

**Индекс файлов.** В git-репозитории список файлов даёт сам git:
отслеживаемые файлы лежат у него в `.git/index`, и `git ls-files` отдаёт их,
не трогая диск. Unity-проект на 272 000 файлов: **поиск работает через
0.23 с**, полный список с новыми файлами готов через 1.1 с. Правила
игнорирования при этом ровно те, что у `git status`, включая глобальный
excludesFile. Запускается настоящий git из Command Line Tools, Xcode или
Homebrew, а не заглушка `/usr/bin/git`, которая без инструментов показала бы
окно установки.

Вне git — собственный обход. Он уважает `.gitignore` каскадно: правила
из вложенных `.gitignore` действуют только на своё поддерево, поддержаны
отрицания (`!`), якоря (`/build`), только-директории (`bin/`) и globs
(`**`, `*`, `?`, `[...]`). Если `.gitignore` нет вовсе, применяется
список типовых мусорных папок (`node_modules`, `obj`, `DerivedData`, …).
Папки читаются через `readdir` — имя и тип одной записью, — все папки
одного уровня параллельно. Правила разбираются заранее: точное имя
сравнивается напрямую, `*.ext` — по окончанию, а перед глобом в пути ищется
его обязательный кусок (`ssets/StreamingAssets/` для
`/[Aa]ssets/StreamingAssets/**/*.bank`), и если его нет, глоб не
запускается. Тот же проект: **0.6 с** против 9.4 с до этого.

**Поиск.** Все относительные пути лежат в одном непрерывном байтовом
буфере, а не в массиве строк — поэтому набор запроса не порождает
аллокаций на файл. Скоринг в духе fzf: бонусы за границы слов, camelCase,
подряд идущие символы, совпадение в имени файла; smart case; учёт того,
насколько запрос покрывает имя файла. Замер: **~25 мс на 100 000 файлов**.

**Дерево файлов.** Боковая панель строится из того же индекса, а не
отдельным обходом диска, поэтому в ней ровно то, что находит `⌘P`, с тем
же `.gitignore`. Сборка дерева идёт в фоне: **~150 мс на 100 000 файлов**.
Под капотом `NSOutlineView` — строки создаются только для видимой части,
а стрелки, `←` `→` и набор имени работают штатно. Клик по файлу выделяет
его, двойной клик и `Return` — открывают и переводят фокус в текст. Открытый файл сам
подсвечивается в дереве: папки до него раскрываются. Стрелка раскрытия
ловит клик на всю высоту строки и с запасом по бокам — штатная мишень
слишком мелкая.

**Кэш индекса.** Список путей пишется в `~/Library/Caches/Pilot/`.
При повторном открытии проекта поиск доступен сразу, а пересканирование
идёт фоном и молча заменяет индекс.

**Слежение за диском.** За деревом проекта следит FSEvents: правка в другом
редакторе, переключение ветки, новый файл — всё это доходит само, без
переоткрытия папки. Система копит события полсекунды и склеивает повторы, но
на Unity-проекте во время компиляции их всё равно тысячи, поэтому первым делом
пачка просеивается по корневому `.gitignore` — `/[Ll]ibrary/` и `/[Tt]emp/`
отсекаются вместе со всем, что под ними. Правку от удаления отличает не флаг
события, а сам диск: флаги FSEvents склеиваются, и «создан» вместе с «удалён»
в одной пачке — обычное дело.

Дальше пачка расходится на три дела. Исходники уходят в ту же переиндексацию,
что и `⌘S`. Появление и исчезновение файлов пересобирает список — целиком и
с задержкой в полторы секунды: правила игнорирования у git свои, и повторить
их один раз в конце дешевле и честнее, чем угадывать по каждому событию.
События под `.git` обновляют ветку и статус. Отдельно оговорено своё же
сохранение: Pilot пишет атомарно, через временный файл и переименование, и
системе это видно как создание файла — список от такого не меняется, и
пересобирать его не нужно. Всё, что стоит проверять, живёт в `FileChanges`
отдельно от FSEvents — и потому попадает в тесты ядра.

**Индекс после правки.** Сохранение файла не заставляет разбирать проект
заново: с диска перечитывается только сохранённый файл, а символы остальных
переносятся из старого индекса как есть — ни чтения, ни лексера на них не
тратится. Собирается при этом новый индекс, а старый продолжает отвечать на
запросы из фона: он неизменяем, и держаться этого дешевле, чем расставлять
блокировки на горячем пути поиска. Остаётся пересборка таблиц поиска по уже
разобранным символам — заметно дешевле полного прохода, но не бесплатно,
поэтому она идёт в фоне и с задержкой. Пачка сохранений (`⌥⌘S`) сливается
в одну пересборку, а пока идёт полный разбор проекта, переиндексация ждёт
его: он и так прочитает файл с диска.

**Подсветка.** Лексер работает в два прохода. Первый — быстрый, по всему
файлу, запоминает только границы строк и состояние лексера на входе в
каждую (внутри ли мы блочного комментария или многострочного литерала).
Второй разбирает **только видимые на экране строки**. Поэтому стоимость
подсветки не зависит от размера файла: **0.45 мс на экран** что на файле
в 200 строк, что в 200 000.

Лексер работает над UTF-16 code units, а не над байтами UTF-8 — так
смещения токенов напрямую совпадают с `NSRange`, и подсветка не разъезжает
на файлах с не-ASCII текстом.

Языки: C#, Swift, C/C++/ObjC, JS/TS, Python, Rust, Go, Java, Kotlin, Ruby,
PHP, shell, SQL, JSON, YAML, TOML, XML/HTML, CSS, Markdown; из Unity — ShaderLab
и HLSL (`.shader`, `.hlsl`, `.cginc`, `.compute`), сериализованные ассеты
(`.unity`, `.prefab`, `.asset`, `.mat`, `.controller`, `.meta`…), `.asmdef`,
`.inputactions`, `.shadergraph` как JSON, `.uxml` и `.uss`.

## Навигация по коду

Разделена надвое сознательно — по тому, нужен ли для неё языковой сервер.

**Без сервера, мгновенно.** Структура файла строится лексером при открытии
(файл на 32 000 строк — 140 мс, в фоне). Отсюда работают `⌘⇧O`, прыжки по
объявлениям `⌃↓`/`⌃↑`, вкладка структуры в навигаторе и jump bar,
показывающий, внутри какого класса и метода сейчас курсор.

Идентификатор под курсором подсвечивается по всему файлу, `⌥↓`/`⌥↑` прыгают
по вхождениям. Совпадения внутри строковых литералов и комментариев
отбрасываются, подстроки не считаются: на `count` не загорится ни `Counter`,
ни `counter`. Устроено так: быстрый проход по всему тексту с проверкой границ
слова, а затем лексятся только те строки, где что-то нашлось — их всегда мало.
Файл на 120 000 строк обрабатывается за 7 мс.

**Действия у курсора (`⌘.`).** Меню прямо под курсором со всем, что можно
сделать там, где он стоит. На символе — перейти к объявлению, найти
использования, пройти по вхождениям, поискать имя по проекту; в конфликте
слияния — принять сторону; на изменённой строке — посмотреть, что было, в
файле MR — прокомментировать; дальше — структура файла, Unity и правка.
Ключевые слова, строки и комментарии символом не считаются. Каждый пункт —
существующая команда, справа её сочетание: меню заодно учит клавишам.
Меню штатное — стрелки, Return, поиск по первым буквам; первый пункт выделен
сразу, так что `⌘.` `Return` — то же, что `⌘B`.

**Поиск по классам (`⇧⇧`)** — как Search Everywhere в JetBrains, но в основном
по типам: классы, структуры, интерфейсы, enum, record, протоколы, трейты.
После индекса файлов тем же лексером и тем же структурным разбором фоном
проходятся все исходники проекта, на всех ядрах: Unity-проект на 1300
`.cs`-файлов — меньше 0.1 с. Индекс кэшируется рядом с индексом файлов,
поэтому при повторном открытии поиск по классам доступен сразу. Матчинг тот же,
что у `⌘P`, с аббревиатурами: `PlPawn` → `PlayerPawn`. Запрос с точкой
(`Components.PlayerPawn`) ищет по полному имени с пространством имён.
`extension` и `impl` в выдачу не попадают — это не новые типы. Под типами —
несколько файлов, если искомое оказалось конфигом или ассетом.

Двойной Shift засчитывается, только если Shift нажат и отпущен сам по себе:
набор заглавных букв и `⌘⇧O` поиск не открывают.

**Предпросмотр в палитре.** Во всех режимах палитры рядом с результатами
виден выбранный файл — с подсветкой и номерами строк, в шрифте редактора.
У класса, символа или использования фрагмент прокручен к нужной строке, а имя
подсвечено; у файла показано начало. Картинки показываются картинкой.
В широком окне предпросмотр справа, в узком — под списком; кнопка в поле
ввода его прячет. Лексятся только строки фрагмента — на файле в 200 000 строк
это 1.5 мс. Недавние файлы кэшируются, а пока держат стрелку, устаревшие
загрузки отбрасываются, не начавшись. Клик по результату выделяет его —
в предпросмотре видно, что там; двойной клик по результату или по
предпросмотру — как Return.

**Быстрый навигатор: `⌘B`, `⌘T`, `⌘R` до Roslyn.** Тем же проходом, что
и индекс классов, собирается индекс всех объявлений проекта — типов, методов,
свойств, полей, значений enum — вместе с их типами, типами параметров,
базовыми классами и `using` каждого файла. На Unity-проекте в 26 000 файлов C# и 2,3 млн строк
это **1,5 с и ~150 МБ** против минут и гигабайтов у Roslyn, а с кэшем
навигатор готов через **2 с** после открытия проекта.

* `⌘B` разбирает `a.b().c` по объявленным типам: поля, свойства, параметра,
  локальной переменной (`Foo x`, `var x = new Foo()`, `var x = Make()`,
  `foreach`), возвращаемого типа метода с подстановкой дженериков
  (`Stash<Health>.Get()` → `Health`). Члены ищутся и в базовых классах,
  из одноимённых типов выбирается тот, чей namespace подключён в файле.
  Если тип выяснить не удалось, а объявлений с таким именем несколько,
  показывается список, ближние первыми. Если тип известен, но он не из
  проекта (`StringBuilder`, `MonoBehaviour`), — честно ничего.
* Перегрузки различаются по числу аргументов в вызове: `Move(1)` ведёт
  к `Move(int)`, `Move(1, 2)` — к `Move(int, int)`. Запятые внутри вложенных
  вызовов и дженериков не в счёт. Если не сошлось ни с одной, показываются
  все: наугад выбранная перегрузка уводит не туда молча.
* Методы-расширения: `p.Say()` находит `static void Say(this Player p)`
  из постороннего static-класса. Индекс держит их отдельной таблицей
  «расширяемый тип → методы», а получателя сверяет тем же резолвом, что и
  всё остальное, — расширение одноимённого типа из чужого namespace
  не подмешается. Свой член при этом всегда важнее расширения, как и в C#.
* `⌘T` — fuzzy-поиск по всем объявлениям, ~10 мс на запрос.
* `⌘R` — слово целиком по исходникам того же языка, без строк и
  комментариев, на всех ядрах; для локальной переменной — только в её файле.
* Поля, которые допишет кодогенератор Morpeh по `[IncludeStash(typeof(X))]`,
  в индексе есть: `_x` типа `Stash<X>`, объявлением считается атрибут.

На 3000 случайных обращениях `x.Member` в таком проекте `⌘B` сразу прыгает
в 53% случаев, в 11% предлагает список, в 35% не находит ничего — почти всегда
это Unity и .NET, чьих исходников в проекте нет. Худший запрос — 1 мс.

**Иерархия вниз: `⌥⌘B`.** Обратная сторона того же индекса. Каждый тип
принёс с собой список базовых из `: Base, IFoo` — если перевернуть его в
таблицу «базовый → наследники», получается переход к реализациям, причём
без второго обхода проекта и без изменений в кэше. На типе показывает тех,
кто его наследует или реализует, — и напрямую, и через промежуточные звенья;
на методе, свойстве, поле — их переопределения. Если реализация одна, туда
и прыгаем, иначе список в палитре. На методе сначала поднимаемся к типу, где
он объявлен впервые: стоя на `override`, ищешь обычно не своё поддерево,
а соседей по базовому классу. Одноимённые базовые из разных namespace
разбираются тем же резолвом, что и `⌘B`, поэтому `: IDamageable` из чужого
проекта в список не попадёт. Роль сервера здесь нулевая: запрос к нему
не уходит вовсе — иерархия целиком известна индексу.

**Переключение на Roslyn — незаметное.** Roslyn отвечает на рукопожатие
через секунды, а solution грузит ещё минуту и дольше, и всё это время его
ответы пусты или неполны. Поэтому доверять ему начинаем, когда он впервые
что-то нашёл: до этого первым отвечает быстрый навигатор, а сервер
опрашивается фоном. После — наоборот: спрашиваем Roslyn, а к индексу
откатываемся, если тот ничего не нашёл. Кто отвечает сейчас, видно в
статус-строке: молния «Индекс» или зелёная точка сервера.

Структурный разбор не семантический: он не знает типов и не резолвит имена
компилятором. Для C-подобных языков, где у метода нет вводного слова, работает
эвристика по форме `Тип Имя(...) {`. Она проверена на реалистичном коде —
вызовы, LINQ, локальные переменные и тела-выражения в структуру не попадают.

## Разбор C#

Всё выше — про то, что Pilot делает своими силами на любом из двух десятков
языков, которые знает его лексер. Для C# есть второй путь, и он про то, чего
лексером не сделать.

Разница не в скорости, а в том, что своя эвристика по форме строки **молча
ошибается**. `Helper(1);` имеет форму объявления метода. `Stash<Health>.Get()`
имеет форму обобщённого. Оба попадают в структуру файла, оттуда — в индекс, а
из индекса — в `⌘B`, и ошибка расходится по всему, что на них построено.
Точно так же `Vector3` в Unity-проекте, где рядом с движковым лежит свой: имя
совпадает, а тип разный, и выбрать между ними можно только областью видимости
на месте обращения — какой `namespace` у файла, какие `using`, какой
псевдоним объявлен.

Поэтому C# читает [Rustlyn](https://github.com/stasiandr/rustlyn) —
компилятор C# на Rust, тот же, что собирает `.dll` и читает метаданные.
Подключён он послойно, и слои отвечают по очереди: каждый следующий дороже
предыдущего и ни один не ждёт того, что над ним.

1. **Открыть файл.** Байты в текст: кодировка (включая BOM, UTF-16 и
   не-UTF-8, который сохраняется байт в байт), перевод строки и отступ — из
   самого файла. Ни разбора, ни лексера. Файл на экране до того, как про
   него что-то решено.
2. **Подсветить.** Настоящий лексер C#: raw-строки, вложенная интерполяция
   (`$$"""{{s.Replace("""a""", """b""")}}"""`), суффикс `u8`, и невзятая
   ветка `#if` — приглушённой, а не как комментарий. Красится **только
   видимый экран**: лексер возобновляется с ближайшей точки возврата выше
   окна, а не с начала файла. На файле в 200 000 строк первый экран — 149 мкс,
   прокрутка — 257 мкс, прыжок в любую строку прогретого файла — 178 мкс;
   прогрев целиком идёт фоном и занимает 0,7 с.
3. **Структура файла.** От парсера, а не от формы строк. Вызов — это вызов,
   локальная функция принадлежит своему методу, а класс в невзятой ветке
   `#if` в файле отсутствует. У каждого объявления заодно есть то, что нужно
   навигатору: тип, типы параметров и как они передаются, базовые, атрибуты.
   Отсюда `⌘⇧O`, jump bar и вкладка структуры.
4. **Индекс проекта.** Те же объявления по всем файлам, на всех ядрах.
   `⌘B` разрешает имя так, как его разрешает C#: `Vector3` в файле с
   `using UnityEngine;` — движковый, в файле без него — свой, а
   `using Vec = UnityEngine.Vector3;` — тот, который назвали. Цепочка
   `_stash.Get().Value` проходится слева направо с типом на руках. Где
   область видимости **не** разрешает, показывается список кандидатов, а не
   первый попавшийся: наугад выбранный вариант уводит молча. `⌥⌘B` идёт по
   той же таблице вниз — наследники и переопределения.
5. **Сборки.** См. «Сборки без исходников» ниже: поверхность сразу, IL
   метода — по запросу.

**Кэш.** Каждый слой — чистая функция от байтов файла, поэтому перед любой
работой стоит один и тот же вопрос: входные данные менялись? Отвечает на него
сначала `stat` — длина и время правки, без чтения; если они сдвинулись, файл
читается и хешируется, и **совпавший хеш засчитывается как «не менялось»**.
Это тот случай, ради которого всё и сделано: `git checkout` туда и обратно
переписывает время у файлов, содержимое которых не изменилось, и стоить это
должно чтения, а не переразбора. Дальше — папка кэша от прошлого запуска.
И только потом работа.

Меряется это так. Проект на 5 000 файлов и 100 000 строк, четыре ядра:
холодная сборка индекса — 512 мс, повторная в том же процессе — 88 мс, при
следующем запуске из кэша на диске — 100 мс, после сохранения одного файла —
84 мс. Разрешение имени — 60 нс.

**Где проходит граница.** Rustlyn — это C#, и только C#. Всё остальное
Pilot открывает, красит и разбирает сам, как раньше. И даже в C# набор текста
остаётся за своим лексером: он инкрементальный и правит модель в том же
вызове, что и текст, — обычное нажатие клавиши перелексирует одну строку. Как
только файл устоялся (открыли, сохранили), отвечает снова Rustlyn. Правила
Unity — какие методы зовёт движок, какие поля он сериализует — тоже остались
здесь: Rustlyn приносит имена и разобранные атрибуты, а что из этого значит
«движок это позовёт», знает Pilot.

Каждый вызов к Rustlyn может ответить «не знаю» — сессии ещё нет, индекс не
собран, файл правят прямо сейчас, — и тогда молча отвечает свой разбор, как
до этого. Ни одна функция при этом не пропадает; она просто отвечает хуже.
Ровно это и проверяют тесты ядра: они собираются без библиотеки вовсе.

## Unity

Pilot сам узнаёт Unity-проект — по `ProjectSettings/ProjectVersion.txt` в
открытой папке или в одной из её подпапок (типичный репозиторий игры). В
статус-строке появляется фишка с версией редактора. Всё ниже работает без
Unity и без языкового сервера.

**Меньше шума.** `.meta` — половина файлов любого Unity-проекта — спрятаны из
`⌘P` и дерева. `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/` не
индексируются, даже если `.gitignore` нет. Заглянуть в `.meta` можно по `⌃⌘M`.

**Индекс GUID.** Сцены и префабы ссылаются на ассеты только по GUID из `.meta`.
Pilot фоном собирает таблицу `GUID → файл` по `Assets/`, `Packages/` и
`Library/PackageCache/` — так резолвятся и скрипты пакетов. Обход идёт через
`fts` и читает только начало каждого `.meta`: **~200 мс на 12 500 ассетов**.

**Сцены и префабы.** Формат Unity разбирается построчно, без YAML-парсера:
сцена на 260 000 строк — **~100 мс** в фоне. Отсюда:

* `⌘⇧O` показывает иерархию: GameObject'ы, их компоненты и вложенные префабы.
  MonoBehaviour называется именем скрипта, а не `MonoBehaviour`; хлебные
  крошки — `Canvas / Panel › Button`.
* `⌘B` или `⌘`+клик по `{fileID: …, guid: …}` открывает ассет — скрипт сразу
  на `class Имя`, префаб — на нужном объекте. По локальной `{fileID: …}` —
  прыжок к объекту внутри файла: по `m_Father`, `m_GameObject`, `component:`
  удобно ходить по иерархии прямо в тексте. Работает и в `.asmdef`
  (`GUID:…`) и в `.meta`.
* GUID подсвечены ссылками, подсказка при наведении показывает путь ассета.
  **Битые ссылки** (Missing Script, пропавший материал) — красные.

**Иерархия в дереве.** У открытой сцены или префаба под его файлом в дереве
проекта раскрывается иерархия — как окно Hierarchy в Unity: GameObject'ы и
вложенные префабы, дети в порядке `m_Children`, корни сцены — по `SceneRoots`
(или `m_RootOrder` в проектах до Unity 2022), выключенные объекты бледные. Клик
по объекту ставит на него курсор, и инспектор показывает его компоненты —
правь прямо там; стрелки `↑` `↓` по иерархии ведут инспектор за собой, `Return`
уводит в текст. Обратно тоже работает: курсор в тексте выделяет свой объект в
дереве и раскрывает его предков. У префаба корень раскрыт сразу, у сцены — нет;
что раскрыто, помнится для каждого файла. Стрелка есть у всех сцен и префабов:
раскрыть неоткрытый — значит открыть его. На реальном проекте иерархии всех
9 700 сцен и префабов (325 000 объектов) строятся за 240 мс — в худшем файле 13 мс.

**Где используется ассет.** `⇧⌘R` на скрипте, префабе, материале, текстуре —
любом файле с `.meta` — ищет его GUID по всем сценам, префабам и ассетам
проекта через `memmem`. В результатах не только файл и строка, но и место:
`Player / Model › Animator`. Десятки переопределений одного вложенного
префаба сворачиваются в одну строку. На проекте с 220 МБ сцен и префабов —
**~60 мс**. Для текстур и моделей, которые не открываются как текст, `⇧⌘R`
тоже работает.

**Инспектор.** У сцен, префабов и ScriptableObject'ов справа есть панель,
как инспектор Unity (`⌥⌘0`). Она показывает объект под курсором: GameObject
со всеми компонентами в порядке `m_Component`, вложенный префаб с его
переопределениями или самостоятельный объект ассета. Над ним — путь в
иерархии, под ним — дети; всё кликается и ведёт в текст. Группы, списки и компоненты
раскрываются кликом по всей строке заголовка, а не только по стрелке.

Значения правятся прямо в панели: имя, активность, тег и слой объекта,
включение компонента, числа, строки, векторы, цвета. Transform — как в Unity:
Position, Rotation углами Эйлера (в файл пишется кватернион и
`m_LocalEulerAnglesHint`), Scale. Тип поля берётся из C#-скрипта: `bool` —
галочка, enum — список значений (enum ищется в самом скрипте и в файле с его
именем), у встроенных компонентов bool узнаётся по имени поля.

Правка из инспектора — это правка текста, как набор: меняется **только
само значение**, файл помечается несохранённым и пишется по `⌘S`, как сцена
в Unity, а `⌘Z` в редакторе отменяет её одним шагом — даже поворот, который
меняет семь чисел. В `git diff` потом ровно изменённые строки. Каждая правка
помнит, что должно лежать на её месте, а после любой правки — из инспектора
или руками — файл разбирается заново: по устаревшим позициям инспектор не
пишет. Кнопка с жуком показывает служебные поля — как Debug-режим инспектора
Unity.

Разбор проверен на всех 1 184 сериализованных файлах реального проекта:
4,9 млн полей, позиция каждого значения совпала с текстом.

**C#.** Методы, которые вызывает движок (`Awake`, `Update`, `OnTriggerEnter`,
`OnValidate`, `OnInspectorGUI`, `OnCreate` из ECS…), выделены цветом и значком
⚡ в колонке номеров, а в `⌘⇧O` помечены как `unity`. Поля с
`[SerializeField]`, `[SerializeReference]` и `[field: SerializeField]`
помечены как `inspector`. Узнаются по имени и атрибуту — как их и находит сам
Unity, — а не по наследованию от `MonoBehaviour`.

**Внешний редактор скриптов.** Двойной клик по скрипту или по ошибке в
консоли Unity открывает файл в Pilot на нужной строке, «Assets → Open C#
Project» — сам проект. Ничего ставить в проект не нужно — в Unity:
Preferences → External Tools → External Script Editor → Browse… →
`Pilot.app`, и в External Script Editor Args:

```
$(ProjectPath) $(File):$(Line):$(Column)
```

На macOS Unity на каждый файл запускает редактор заново — новым процессом,
с аргументами в командной строке. Если этот же `Pilot.app` уже открыт,
новый процесс передаёт ему файл Apple Event'ом (адрес
`pilot://open?file=…&line=…`) и сразу выходит: окно одно, вкладки и
прогретый индекс остаются. Сборки из других папок с тем же идентификатором
не считаются — у каждой своё окно. Файл из другого проекта переключает
Pilot на тот проект; корнем становится папка Unity-проекта, а без
`$(ProjectPath)` — ближайший git-репозиторий над файлом.

`.sln` и `.csproj` Unity сама не пишет — это делает пакет выбранного
редактора, а у Pilot пакета нет. Пока в Preferences выбран Pilot, файлы
проекта не обновляются: новый скрипт или asmdef языковой сервер увидит,
когда они будут перегенерированы — например, «Regenerate project files»
с выбранным на минуту Rider.

Pilot это видит и говорит вслух. Если `.sln` и `.csproj` нет вовсе или
Unity компилировала скрипты позже, чем их писали (видно по датам
`Library/ScriptAssemblies`), об этом сказано в подсказке у значка Unity
в статус-строке, а `⌘B`, которому нечего ответить, называет причину
прямо — вместо молчания, похожего на сломанную клавишу. Solution при
этом ищется не только в корне открытой папки, но и в папке
Unity-проекта, если он лежит в подпапке репозитория: иначе сервер
поднимался бы вообще без проектов.

Из Finder и `open -a Pilot File.cs` файлы тоже приходят в уже открытое окно.

## Языковой сервер (C#)

Семантика C# — это Roslyn, а Roslyn грузит solution и строит индекс
символов. На Unity-проекте из 134 csproj это 7 с и ещё около минуты.

Поэтому LSP здесь встроен по одному жёсткому правилу: **он никогда не
блокирует интерфейс**. Пока сервер греется, поиск по файлам, просмотр и
подсветка работают на полной скорости и о его существовании не знают, а
`⌘B`, `⌘T` и `⌘R` отвечает быстрый навигатор. Прогресс виден в капсуле
активности в тулбаре — «проекты 57 из 134»; когда точка рядом с именем
сервера загорается зелёным, навигация уже идёт через него.

Если в корне проекта лежит solution, Roslyn поднимается сразу при открытии
проекта: пока ищешь нужный файл, он успевает загрузиться. Прочие серверы —
при первом файле своего языка.

Готовым сервер считается не после `initialize` (у Roslyn это полсекунды),
а когда он сообщает, что загрузил все проекты
(`workspace/projectInitializationComplete`). До этого он отвечает, но
пустотой. Сразу после загрузки фоном прогревается индекс символов. Roslyn
строит его в две стадии, и каждую запускает очередной `workspace/symbol`
(на том же проекте — 35 с и 22 с), поэтому прогрев — два запроса подряд,
ни с чем не совпадающих. После этого `⌘T` отвечает за доли секунды.

**Демон (экспериментально, выключен по умолчанию).** Включается в меню
«Pilot → Экспериментальное → Держать языковые серверы между запусками»;
сервер текущего проекта при переключении поднимается заново.

Всё это — загрузку и прогрев — не хочется повторять при каждом запуске
Pilot. Поэтому серверы живут в отдельном процессе-демоне: это тот же
исполняемый файл Pilot с флагом `--lsp-daemon`, Pilot сам запускает его при
первой необходимости и подключается по unix-сокету. Дальше по сокету идёт
обычный LSP, а демон отвечает от имени уже прогретого сервера. Закрыл Pilot,
открыл снова — Roslyn уже готов, индекс символов тёплый.

Демон держит один сервер на проект, даже если его открыли два окна Pilot:
общий документ открывается на сервере один раз и закрывается, когда его
закрыл последний клиент. Серверы без клиентов живут так:

* поднимается быстрее 4 с — останавливается сразу: игрушечный проект
  перезапустится раньше, чем это заметишь;
* дорогие держатся до двух суток простоя, не больше пяти одновременно;
* суммарно без клиентов — не больше 32 ГБ: это страховка от утечки, а не
  экономия. Прогретый Roslyn на Unity-проекте занимает 4–6 ГБ.

Когда держать нечего, демон выходит сам; выключили его в меню — уходит сразу
вместе с серверами. Пересобрали Pilot — демон от старой сборки уступает место
новому. Процесс демона называется так же, как приложение, поэтому
`pkill -x Pilot` из `run.sh` убивает и его. Журнал демона —
`~/Library/Caches/Pilot/lspd.log`; `PILOT_LSP_DAEMON=1` или `=0` в окружении
перекрывает настройку из меню.

Две настройки — про `⌘B` в сборку без исходников: сервер декомпилирует
тип сам и отдаёт путь к `.cs` в своём кэше (см. «Сборки без исходников»).
Остальные настройки Roslyn выбраны под чтение кода, а не под сборку. Главное —
выключен автоматический NuGet restore: по умолчанию Roslyn гоняет его для
каждого проекта по очереди, и на Unity-проекте из 134 csproj это была минута
из полутора — впустую, в сгенерированных Unity проектах восстанавливать
нечего. Выключены и диагностики: Pilot их не показывает.

Второе — Mono. Старые, не-SDK csproj (а Unity генерирует именно такие)
Roslyn загружает через Mono, если находит его в PATH, — а Pilot, запущенный
из терминала, наследует PATH оболочки, куда Mono прописывает установщик.
Через .NET те же проекты грузятся втрое быстрее с тем же результатом,
поэтому из PATH сервера Mono убирается. Вместе: загрузка того же solution —
**7 с вместо 84**.

Сервер ищется в системе в таком порядке, берётся первый установленный:

1. **Roslyn** (`Microsoft.CodeAnalysis.LanguageServer`) — тот же сервер,
   что стоит за C# Dev Kit в VS Code. Лучшая семантика, самый долгий
   прогрев. Находится автоматически в `~/.vscode/extensions/ms-dotnettools.csharp-*`.
2. **csharp-ls** — лёгкая обёртка над тем же Roslyn.
   `dotnet tool install --global csharp-ls`
3. **OmniSharp** (`omnisharp -lsp`) — старый, но ещё встречается.

Для Swift есть встроенный **SourceKit-LSP** — он идёт вместе с Xcode и
Command Line Tools, ставить ничего не надо. SwiftPM-проекты он понимает
сам, по `Package.swift`, и индексирует их в `.build/index-build`.

Если в корне лежит `.sln`, он передаётся серверу явно: без этого Roslyn и
csharp-ls угадывают, что грузить, и часто угадывают не то.

Свои серверы — в `~/.config/pilot/servers.json`. Клиент к C# не привязан,
это обычный LSP:

```json
{
  "servers": [
    {
      "id": "csharp-custom",
      "displayName": "Roslyn",
      "languageId": "csharp",
      "extensions": ["cs", "csx"],
      "command": ["/path/to/Microsoft.CodeAnalysis.LanguageServer", "--stdio"],
      "opensSolution": true,
      "projectsLoadedNotification": "workspace/projectInitializationComplete",
      "settings": { "projects.dotnet_enable_automatic_restore": false }
    },
    {
      "id": "gopls",
      "displayName": "gopls",
      "languageId": "go",
      "extensions": ["go"],
      "command": ["gopls"]
    }
  ]
}
```

## Сборки без исходников

Кода, которого нет в проекте, здесь два пути: `⌘B` на типе из сборки — и
сама сборка, открытая как файл.

**`⌘B` на `Vector3`** ведёт в код с телами методов. Декомпилирует его
Roslyn (внутри у него тот же ILSpy): по просьбе он разбирает один тип,
пишет настоящий `.cs` в свой временный кэш и отдаёт путь к нему обычным
`Location`. Pilot открывает этот файл как любой другой — с подсветкой,
структурой и комментариями из XML-документации, — и `⌘B` изнутри работает
дальше: из `Vector3` в `Math`, из `Math` в её сборку. Вкладка помечена
коробкой и только для чтения: файл и на диске такой, а правки девать
некуда. Между запусками такие вкладки не помнятся — временный кэш
сервера вычищается.

Если у сборки есть PDB с вшитыми исходниками или Source Link, сервер
отдаёт настоящий код, а не декомпиляцию — как это делает Rider.

Работает это через прогретый Roslyn, поэтому пока он грузится, отвечать
на `⌘B` нечем. Раньше в ответ была тишина, теперь — строка в тулбаре:
«Объявление знает языковой сервер — он ещё запускается (проекты 57 из
134)».

**Когда сервера нет.** Свежий клон Unity-проекта — это проект без
`.csproj`: пишет их не Unity, а пакет выбранного редактора, и в git они
не попадают. Грузить Roslyn'у нечего, и `⌘B` по `Vector3` в такой папке
раньше молчал. Теперь отвечает индекс сборок: Pilot читает имена типов
из всех `.dll` проекта — плагинов, библиотек пакетов — и из сборок
самого редактора Unity. Где он стоит, Unity записывает в
`Library/EditorInstance.json`; если проект ни разу не открывали, путь
складывается из версии в `ProjectVersion.txt` и обычного места установки
Hub. `⌘B` открывает сборку на объявлении типа, `⇧⇧` показывает эти типы
под проектными. Читаются только имена из таблицы типов: 3 500 типов из
160 сборок — 350 мс на холодном диске, 20 мс на тёплом, и всё это фоном.
Положили в проект новый плагин — индекс подхватит его вместе с очередным
обходом проекта, тем же, которым за диском следит список файлов.
Тел методов такой переход не даёт — их даёт только Roslyn; зато он
работает всегда.

**Сама `.dll`** (а также `.exe` и `.winmd`) открывается как обычный файл —
только вместо байтов видны её объявления на C#. Это то, ради чего обычно
открывают ILSpy: что за типы внутри плагина, какие у них методы и
константы, чем отличаются перегрузки. Сервер для этого не нужен: разбор
свой и мгновенный, зато без тел методов.

Читаются метаданные: PE → заголовок CLI → таблицы
ECMA-335. Типы раскладываются по пространствам имён, у каждого —
доступность, базовый тип и интерфейсы, параметры обобщения с
ограничениями, поля с константами, свойства с аксессорами, события,
методы с именами параметров и значениями по умолчанию, атрибуты вместе с
аргументами. Перечисления идут со значениями членов, делегаты — строкой,
расширяющие методы — с `this`. Имена типов короткие: своё пространство
имён, `System` и пространства самой сборки в исходнике закрыл бы `using`,
а вот чужое пишется целиком — по нему и видно, из какой библиотеки тип.

Быстро настолько, что ждать нечего: Newtonsoft.Json (700 КБ) — 5 000
строк за 50 мс, `System.Runtime` — 15 000 строк за 130 мс. Дальше это
обычный C#-текст: подсветка, структура файла (`⌘⇧O`), поиск (`⌘F`) и
переходы по объявлениям внутри самой сборки (`⌘B`).

**Тела методов — по запросу.** `⌘.` на строке с объявлением метода
показывает его IL, отдельной вкладкой и только для чтения. Это второй
вопрос к сборке, и задаётся он по одному методу: поверхность — это проход
по таблицам и ни одной инструкции, а тело читается у того метода, который
открыли. На `System.Runtime` разница между «показать объявления» и
«показать всё» — это разница между кадром и минутой.

Инструкции идут с разрешёнными именами: `call System.Console::WriteLine`,
а не `call 0x0A000012`; `ldstr` показывает саму строку; чтение поля
называет поле; переход ведёт к метке, а не к смещению; `try`/`catch`/
`finally` размечены. Это **IL, а не восстановленный C#**, и так и
подписано: перевод IL обратно в исходник — отдельная программа (ILSpy
внутри Roslyn делает именно это), и честный дизассемблер полезнее
уверенной выдумки. За настоящим C# с телами — к языковому серверу, выше.

Без Rustlyn тел нет вовсе, как и раньше: в метаданных лежит IL, а свой
читатель метаданных его не разбирает. Вкладка помечена коробкой и только для чтения: правки
такому тексту некуда сохранять, и языковой сервер про него не знает —
на диске по этому пути сборка, а не код. Нативная библиотека без
.NET-метаданных так и говорит о себе — читать в ней нечего.

Сборки, собранные Unity, лежат в `Library/ScriptAssemblies`, а эта папка
в индекс не попадает: их открывают из Finder или `open -a Pilot`. Плагины
из `Assets/Plugins` и пакетов видны в `⌘P` и в дереве как обычные файлы,
а в палитре у них тот же предпросмотр, что у исходников.

## Git

То, что нужно читателю: что поменялось, кто и когда это написал. Коммитов,
стейджинга и веток здесь нет — для этого есть терминал.

* **Полоски у номеров строк** — отличия открытого файла от HEAD: зелёная —
  добавлено, жёлтая — изменено, красный треугольник — здесь удалены строки.
  `⌃⌥↓`/`⌃⌥↑` прыгают по блокам и выделяют блок целиком. Клик по номеру
  изменённой строки показывает, что было на её месте.
* **Автор строки под курсором** — в статус-строке: кто, когда и сообщение
  коммита; в подсказке — хэш и точная дата, правый клик копирует хэш.
* **Ветка** — там же, с `↑`/`↓` относительно upstream и числом изменённых
  файлов. Клик по ней, как и `⌃⇧G`, открывает палитру изменённых файлов
  с тем же fuzzy-поиском, что у `⌘P`.
* **Статус файлов** — буквой в `⌘P` и цветом в дереве: `M` изменён, `A`
  добавлен, `?` не отслеживается, `R` переименован, `U` конфликт. Папка
  с изменениями внутри помечена точкой.

Сравнение идёт с HEAD, а не с индексом: застейдженная правка — всё ещё
правка, пока её не закоммитили.

Git здесь, как и LSP, **никогда не блокирует интерфейс**: это системный
`git`, запущенный в фоне, а результат, опоздавший к уже закрытому файлу,
выбрасывается. Полоски считаются не `git diff`, а своим Myers по двум
снимкам — тексту на экране и блобу из HEAD, — поэтому не разъезжаются,
даже если файл тем временем поменяли в другом редакторе: **~75 мс на файл
в 100 000 строк** с десятком правок. Blame тоже считается
по тексту на экране (`--contents`), с задержкой в 350 мс — пока листаешь
файлы через `⌘P`, на промежуточные он не запускается.

Состояние перечитывается при возврате в приложение: закоммитили или
переключили ветку в терминале — полоски и статус обновятся сами, без
опроса по таймеру. Если git не установлен или проект не под git, ничего
из этого просто не появляется.

## Конфликты слияния

Файл с маркерами `<<<<<<<` открывается как обычно, а конфликты в нём
видны сразу: текущее (HEAD) — на зелёной полосе, входящее — на синей,
общий предок (в стиле `diff3`) — на серой, строки маркеров — на персиковой.

* **У каждого `<<<<<<<`** — кнопки прямо в тексте: «Текущее», «Входящее»,
  «Оба» и, если git записал предка, «База». Решение — обычная правка
  редактора: отменяется `⌘Z`.
* **С клавиатуры** — `⌃⌥⌘↓`/`⌃⌥⌘↑` по конфликтам, `⌃⌥⌘←` оставить
  текущее, `⌃⌥⌘→` взять входящее в конфликте под курсором (или в ближайшем
  ниже).
* **Полоса над редактором** — «конфликт 2 из 5», «Все текущие» и «Все
  входящие» для файла целиком. Когда маркеров не осталось — «Сохранить и
  отметить решённым»: файл сохраняется и уходит в `git add`, для git это и
  значит «решено». Пока маркеры есть, отметить нельзя — иначе в коммит
  уйдёт текст с `<<<<<<<`.
* **Какие файлы ещё в конфликте** — в `⌃⇧G` они первыми, с буквой `U`.

Маркеры ищутся на каждой правке — это проход только по началам строк:
**0,2 мс на файл в 100 000 строк**. Метки берутся из самих маркеров,
поэтому при rebase «текущее» — это ветка, на которую переносятся коммиты,
как и у git.

## Ревью мерж-реквестов (GitLab)

Вкладка «Ревью» в навигаторе (`⌥⌘R`) — открытые MR проекта, сверху те,
где вы ревьюер. Проект определяется по remote репозитория (`origin`),
self-hosted GitLab тоже подходит.

* **Поиск** — поле внизу списка, `⌥⌘R` ставит в него курсор. Загруженные
  открытые MR фильтруются сразу: каждое слово должно найтись в названии,
  ветке, метках или имени автора и ревьюеров; регистр и «ё» не важны.
  `!123` — MR с этим номером, `@логин` — автор или ревьюер. Параллельно
  спрашивается GitLab — он добавляет раздел «Ещё в GitLab»: слитые и
  закрытые MR и найденные по описанию. `Return` открывает верхний
  результат, `Esc` очищает поле.
* **Код — в версии MR.** Файл открывается таким, какой он в голове MR, а
  не в рабочей копии: ветку переключать не нужно, рабочая копия не
  трогается. Такой файл только для чтения — его правки некуда сохранить.
  На вкладке он помечен значком MR; следующий файл MR занимает вкладку
  предыдущего, а выход из ревью закрывает их все.
  Полоски — против базы MR, ровно те же, что в диффе GitLab.
  `⌥⌘↓`/`⌥⌘↑` — следующий и предыдущий файл MR.
* **Что удалено** — клик по номеру строки: над тредами показаны строки,
  которые этот блок заменил.
* **Треды у строк** — значок в гаттере; клик открывает тред рядом со
  строкой: ответить, решить, открыть снова. `⌥⌘]`/`⌥⌘[` — по тредам файла.
  Треды к прошлым версиям MR помечены: строка могла сдвинуться.
* **Новый комментарий** — `⌥⌘C` на строке с курсором, пункт в контекстном
  меню или клик по номеру строки. Markdown, отправка — `⌘↩`.
* **Файлы MR** — со счётчиками `+`/`−` и тредов; «просмотрено» отмечается
  галочкой и хранится локально, пока в MR не запушат новую версию.
* **Апрув** — в полосе ревью над редактором и в навигаторе; апрувится
  именно просмотренная версия (`sha` головы MR), и если в MR успели
  запушить, GitLab откажет. Общие комментарии к MR — внизу навигатора.

Текст файлов берётся из локального репозитория, если коммиты MR уже
скачаны, иначе — через API. Номера строк комментариев сопоставляются по
диффу GitLab; сверено на 484 файлах реальных MR, 117 000 неизменённых
строк — без единого расхождения.

**Подключение.** Нужен Personal Access Token с правами `api` — ссылка на
его создание есть в окне подключения. Pilot проверяет токен запросом
`/user` и кладёт его в связку ключей macOS; в файлы и настройки он не
попадает. Приложение подписано ad-hoc, поэтому после пересборки macOS
один раз спросит доступ к ключу — «Всегда разрешать».

## Ограничения

* Unity: вложенные префабы без переопределённого имени называются именем
  файла префаба, а не именем его корневого объекта. `fileID` внутри моделей
  (`.fbx`) и спрайтшитов не резолвятся — открывается сам ассет. Индекс GUID
  не следит за диском, как и индекс файлов. Иерархия в дереве — только у
  открытого файла; содержимое вложенного префаба в ней не разворачивается —
  он одна строка, как свёрнутый префаб в Unity.
* Инспектор Unity правит только значения полей: не добавляет и не удаляет
  элементы списков и компоненты, не меняет ссылки на объекты и ассеты и не
  правит строки, перенесённые на несколько строк файла — их правят в тексте.
* Нет поиска и замены по проекту, мультикурсора, переноса строк.
* Уже открытая вкладка не перечитывается: индекс, дерево и git за диском
  следят, а текст в буфере — нет. Файл, изменённый снаружи, на экране
  останется прежним, и сохранение поверх него перезапишет чужие правки.
* Закрытие окна красной кнопкой с несохранёнными правками спрашивает
  уже после того, как окно закрылось: при отмене Pilot остаётся запущенным
  без окна, правки при этом живы в памяти.
* Нет поиска по содержимому (`⌘⇧F`).
* Конфликты решаются целым блоком: взять часть строк с одной стороны и
  часть с другой можно только правкой руками, трёхпанельного сравнения нет.
* Git — только для чтения: нет коммитов, стейджинга, истории файла и
  просмотра диффа целиком — только полоски и автор строки.
* Ревью: комментарий ставится к одной строке, многострочных комментариев
  и suggestions нет; к удалённой строке — только через веб. Переход к
  определению в файле MR — только лексический: языковой сервер видит
  рабочую копию, а не версию MR.
* Открытая `.dll` показывается объявлениями: тел методов в ней нет —
  за ними идут через `⌘B` и языковой сервер. Индекс сборок знает только
  типы верхнего уровня и только по имени: перегрузки, вложенные типы,
  члены и `⌘T` — это Roslyn. Аргумент-атрибут, оказавшийся перечислением
  из другой сборки, печатается числом с приведением —
  `(AttributeTargets)1028`: какого размера чужое перечисление, из этих
  метаданных не видно.
* Подсветка лексическая, не семантическая: `Foo` считается типом потому,
  что с заглавной буквы, а не потому, что это класс.
* Перегрузки навигатор различает только по числу аргументов: типы он не
  сверяет, а `params` и значения по умолчанию сбивают счёт — тогда показываются
  все кандидаты. И свой член всегда важнее метода-расширения, даже когда по
  типам аргументов подошло бы расширение.
* Методы-расширения видны только объявленные в проекте и только записанные
  буквально — `this` у первого параметра. Расширения из сборок без исходников
  (LINQ, `UnityEngine`) навигатору взять неоткуда. Расширение массива
  (`this T[] items`) не находится: массив и в остальном не считается типом.
* Быстрый навигатор не выводит типы из лямбд и LINQ, а о сборках без
  исходников знает только имена типов: их члены — дело Roslyn. `⌘R` до
  его готовности ищет по тексту: одноимённые члены разных типов попадут
  в выдачу вместе.
* Реализации (`⌥⌘B`) видят только исходники проекта и только написанное
  буквально: наследник, у которого базовый тип подставляет кодогенератор,
  в список не попадёт, а у типа из сборки без исходников наследников взять
  неоткуда. Дженерики в наследников не подставляются: `Stash<Health>` там
  виден как `Stash`. Больше 500 наследников не показывается — такой список
  всё равно не читают.
* Подсветка вхождений работает по тексту, а не по смыслу: две разные
  переменные с одинаковым именем загорятся вместе.
* Из возможностей LSP подключены определение, использования, символы
  проекта и автодополнение. Нет диагностик, переименования, форматирования
  и подсказок параметров.
* Слежение за диском отсеивает шум по корневому `.gitignore`: вложенные
  `.gitignore` при этом не читаются, и файл, скрытый только ими, вызовет
  лишнее пересканирование списка — на ответы это не влияет, но работа
  проделается впустую. События под `.git` считаются сменой ветки и обновляют
  статус, что бы там ни поменялось на самом деле.
* Файл, удалённый с диска, но ещё не закоммиченный, остаётся в индексе
  git-репозитория: проверка стоила бы `lstat` на каждый файл проекта, а это
  секунды на крупном проекте.
* Поиск по классам и быстрый навигатор лексические: тип, объявленный макросом
  или кодогенерацией, они не найдут (кроме стэшей Morpeh). Для этого есть
  `⌘T` через языковой сервер.
